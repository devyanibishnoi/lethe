Making "your data has been deleted" a provable claim, not a promise.

Lethe is a database-native deletion layer for RAG knowledge bases. Most vector databases only soft-delete on request, the embedding stays physically recoverable on disk. Lethe hard-deletes it, rebuilds only the affected partition, and produces a cryptographically signed, hash-chained audit record proving the deletion actually happened.

The gap

Soft-delete isn't deletion

Enterprises increasingly ground LLM outputs in their own private data through Retrieval-Augmented Generation, backed by HNSW- or IVF-indexed vector databases. When a data subject exercises their GDPR Article 17 right to erasure, most implementations simply flag the record as removed, the underlying embedding remains physically present and recoverable directly from the index files on disk. For a service whose core trust guarantee is that client data stays under client control, that's not a peripheral bug, it's the whole promise, broken.

The approach

How Lethe closes it

Efficient hard-delete at scale, and proof that it happened, without a full index rebuild every time.

01

Partitioned index

The vector index is partitioned by tenant, so one deletion only ever rebuilds the affected shard, not the whole dataset.

02

Hash-chained audit log

Every deletion is signed with ECDSA and chained to the entry before it, so tampering with history, not just one row, is detectable.

03

Cascading erasure

A real erasure request names a person, not a document ID. One request finds and hard-deletes every document a subject has, across every tenant.

04

Benchmarked, not asserted

Deletion latency, index-rebuild cost, and recall@k before/after deletion are all measured across increasing corpus sizes, not just claimed.

What actually happened while building this

Engineering notes

Three real findings from building and benchmarking this, kept rather than cleaned up out of the story.

Bug found

A one-character difference that breaks a cryptographic signature

The deletion certificate embeds a timestamp inside the signed message. Python's default string formatting for a datetime and the JSON API's default encoding differ by exactly one character, a space versus a T. ECDSA verifies an exact byte string, so that was enough to make an otherwise-valid signature fail re-verification. Fixed by making the certificate emit the literal string that was actually signed, not a value that merely represents the same timestamp.

Performance insight

Index rebuild cost scales worse than linearly

Going from 1,000 to 5,000 documents, 5x the data, made the HNSW rebuild roughly 8x more expensive, not 5x. Consistent with HNSW's own insertion cost rising as the graph grows, and the actual numeric evidence behind "HNSW is costlier to update than it is to query," not just an assumption carried over from the literature.

Open question

One unexplained signature, and what to do when you can't find the cause

During one benchmark run, a single signature out of 71 failed self-verification, with no reproducible root cause after ruling out stale keys, timestamp collisions, and duplicate documents. It didn't recur across two further runs. Rather than leave it silently possible, the signing function now verifies its own signature immediately after producing it and refuses to write the row if that check fails, catching a future occurrence loudly, at the source, instead of discovering a bad row cold during an audit.
