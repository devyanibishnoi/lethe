Certified Forgetting
Database systems / applied cryptography

Making "your data has been deleted" a provable claim, not a promise.

Lethe is a database-native deletion layer for RAG knowledge bases. Most vector databases only soft-delete on request, the embedding stays physically recoverable on disk. Every Lethe deletion rewrites the affected tenant's partition, table and vector index together, and produces a cryptographically signed, hash-chained audit record. Not just claimed: a raw search of the actual bytes on disk, the same technique that exposes the problem in the first place, found the deleted embedding in 0 of 20 trials, heap, HNSW, and ivfflat, all three.

The gap

Soft-delete isn't deletion

Enterprises increasingly ground LLM outputs in their own private data through Retrieval-Augmented Generation, backed by HNSW- or IVF-indexed vector databases. When a data subject exercises their GDPR Article 17 right to erasure, most implementations simply flag the record as removed, the underlying embedding remains physically present and recoverable directly from the index files on disk. For a service whose core trust guarantee is that client data stays under client control, that's not a peripheral bug, it's the whole promise, broken.

The approach

How Lethe closes it

A partition-scoped rewrite on every deletion, never the whole dataset, a signed and chained audit trail, and erasure that's checked against the raw bytes on disk, not assumed from the operations that are supposed to produce it.

01

Partitioned index

The vector index is partitioned by tenant, so one deletion only ever rebuilds the affected shard, not the whole dataset.

02

Hash-chained audit log

Every deletion is signed with ECDSA and chained to the entry before it, so tampering with history, not just one row, is detectable.

03

Cascading erasure

A real erasure request names a person, not a document ID. One request finds and hard-deletes every document a subject has, across every tenant.

04

Verified at the byte level

Every deletion claim here is checked against the literal bytes Postgres writes to disk, the same technique that exposes the problem in a soft-delete system, not inferred from a query through the database.

What we actually proved, not just claimed

The verification ledger

Four claims about how deletion actually behaves, each one tested against the real bytes on disk or a live concurrent workload. Two of them were wrong, caught before they shipped, not after.

Claim tested

"Rebuilding the index makes the deleted vector unrecoverable."

method: raw byte search of the index files on disk, 20 trials
13 / 20 Overturned

The deleted embedding's bytes were still physically present in the rebuilt HNSW and ivfflat files. Root cause: the index rebuild ran inside the same database transaction as the delete, before it ever committed.

Fix applied

Moved the index rebuild to run after commit, not inside it.

method: same byte search, rerun against the real deletion path
0 / 20 Confirmed

Reproduced twice before trusting it: once as an isolated test, once against the actual production code, not a parallel copy of it.

Claim tested

"This design doesn't block concurrent reads, only the heavier alternative does."

method: a background thread looping real search queries during a live delete, 5 trials per design
5 / 5 Overturned, both designs blocked

A plain index rebuild turns out to hold a lock strong enough to stall an ordinary search for its full duration, ~390ms, nearly identical to the "heavier" alternative's ~402ms. An assumption carried over from general Postgres knowledge, never checked against this code, until it was.

Design decision

Switched to a single full rewrite of the partition on every delete.

method: same byte search, heap and both indexes, against production
0 / 20 Heap, HNSW, and ivfflat, all clean

With the concurrency cost already a wash, there was no reason left to keep the heap-level gap open. First point in the whole investigation where every location checked comes back clean at once.
